# Paya Coaching

Paya Coaching is a Persian-language educational consulting platform for managing students, study resources, exam analysis, online exams, consultation records, and daily work reports.

The application has separate experiences for consultants and students. Consultants manage educational content and student activity from an administrative panel, while students use a dedicated dashboard to access assigned material, take timed exams, review results, and submit reports.

The frontend is a React single-page application. Authentication, PostgreSQL data, Row Level Security, database functions, and server-side operations are provided by Supabase. Large files are uploaded directly to ArvanCloud Object Storage through short-lived presigned URLs generated by Supabase Edge Functions.

## Main features

### Student account and authentication

- Phone-number registration with OTP verification
- OTP delivery through a custom Supabase Auth hook and sms.ir
- Phone number and password login for students
- Email and password login for administrators
- Password recovery with OTP verification
- Required profile completion after registration
- Persistent sessions with protected, role-aware routes

### Student panel

- View personal profile and educational information
- Access files and links shared by the consultant
- Review consultation history and educational reports
- Upload PDF work reports for a selected date
- View assigned online exams and their current status
- Start timed exams, save answers automatically, and submit attempts
- View the final score of completed exams

### Administration panel

- View dashboard statistics
- Search and manage students
- Edit student profile information
- Record and manage consultation history
- Upload private files for individual students
- Share common files and external links
- Create and publish public exam-analysis pages
- Attach videos and PDF files to an exam analysis
- Create timed online exams from a PDF and an answer key
- Assign each online exam to selected students
- Review attempts, answers, scores, and completion status
- Delete student accounts through a server-side function

### File handling

- Direct browser-to-storage uploads using presigned URLs
- Multipart uploads for large files
- Upload progress, retry handling, cancellation, and stalled-upload detection
- Separate public and private buckets
- Short-lived signed download URLs for protected files
- Server-generated object keys and ownership checks
- Metadata stored in PostgreSQL while binary files remain in object storage

## Architecture

The application is split into three main layers:

1. **React client** — renders the public website and the two authenticated panels, manages forms and client state, and communicates with Supabase.
2. **Supabase backend** — provides Auth, PostgreSQL, Row Level Security, database triggers, RPC functions, and Edge Functions.
3. **ArvanCloud Object Storage** — stores public exam media and private student, online-exam, and work-report files.

The browser never receives the Supabase service-role key or ArvanCloud credentials. Operations that require elevated access are performed inside Edge Functions after validating the caller's access token and application role.

## Authorization model

Application users have either an `admin` or `student` role. The role stored in `public.profiles` is the source of truth; authorization does not rely on client-editable user metadata.

Row Level Security is enabled on application tables. In general:

- students can read only their own profile, records, assignments, attempts, and private content;
- students can upload and manage only their own work reports;
- administrators can manage students, consultations, educational content, and exams;
- anonymous visitors can read only published exam-analysis content;
- private file access is checked server-side before a signed URL is created.

Online-exam answer keys are not returned by student-facing queries. Exam timing, attempt finalization, and scoring are enforced in the database rather than trusted to the browser.

Feature code under `src/features` is grouped by domain:

- `online-exams` — assignments, attempts, autosave, and results
- `work-reports` — student PDF report uploads and deletion
- `dashboard` — administrative statistics

## Database overview

The main application tables are:

| Table | Purpose |
| --- | --- |
| `profiles` | User role and student profile information |
| `student_contents` | Private files and links assigned to a student |
| `consultations` | Student consultation history |
| `exam_analyses` | Published and draft exam-analysis pages |
| `exam_analysis_files` | Public video and PDF attachments for exam analyses |
| `online_exams` | Timed exams, schedules, PDFs, and protected answer keys |
| `online_exam_assignments` | Per-student access to online exams |
| `online_exam_attempts` | Answers, timing, status, and calculated scores |
| `work_reports` | Student-submitted PDF work-report metadata |
| `multipart_uploads` | Ownership records for active multipart uploads |
| `otp_send_attempts` | OTP rate-limit records |

All schema changes are stored as SQL migrations in `supabase/migrations`.

## Edge Functions

The Edge Functions cover operations that require trusted credentials or additional authorization:

- OTP request and SMS delivery
- Presigned single-part upload creation
- Multipart upload creation, part signing, completion, and cancellation
- Signed download URL creation
- Finalizing shared-content and work-report uploads
- Storage object deletion
- Exam media upload and deletion
- Student account deletion

Shared authentication, CORS, phone validation, upload validation, and storage configuration live in `supabase/functions/_shared`.

## Local development

### Prerequisites

- A current Node.js LTS release
- npm
- Docker Desktop or another Docker-compatible runtime for local Supabase
- A Supabase account when working with the remote project

### Install the project

```bash
git clone https://github.com/alizdevco/edu.git
cd edu
npm install
```

Create a local frontend environment file:

```bash
cp .env.example .env
```

On Windows Command Prompt, use:

```cmd
copy .env.example .env
```

Set the following values in `.env`:

```env
VITE_SUPABASE_URL=https://your-project-ref.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
```

These two variables are intentionally available to the browser. Access control must remain enforced by RLS and server-side authorization. Never add the service-role key or storage credentials to a `VITE_` variable.

Start the frontend:

```bash
npm run dev
```

The development server uses `http://127.0.0.1:5173` by default.

## Local Supabase setup

Log in, link the project when remote access is needed, and start the local stack:

```bash
npm run supabase:login
npm run supabase:link
npm run supabase:start
```

To rebuild the local database from the committed migrations and seed file:

```bash
npx supabase db reset
```

Useful commands:

```bash
npm run supabase:status
npm run supabase:stop
```

The local Auth configuration contains test OTP values, so sending real SMS messages is not required for normal local development.

## Server-side secrets

The following values belong in Supabase Edge Function secrets, not in `.env` or frontend code:

```env
SUPABASE_SERVICE_ROLE_KEY=

ARVAN_ACCESS_KEY=
ARVAN_SECRET_KEY=
ARVAN_ENDPOINT=
ARVAN_PRIVATE_BUCKET=
ARVAN_PUBLIC_BUCKET=

SMS_IR_API_KEY=
SMS_IR_TEMPLATE_ID=
SMS_IR_OTP_PARAM_NAME=Code
SEND_SMS_HOOK_SECRET=
```

They can be configured with the Supabase CLI:

```bash
npx supabase secrets set --env-file ./secrets.env
```

Keep `secrets.env` outside version control and remove it after use.

## OTP delivery

Supabase Auth generates and validates OTP codes. The `send-sms` Edge Function is registered as the Supabase Send SMS hook, verifies the hook signature, and forwards the code to the sms.ir Verify API.

For a remote environment:

1. enable the Phone provider in Supabase Auth;
2. deploy the `send-sms` Edge Function;
3. register its URL as the Auth Send SMS hook;
4. configure the same `SEND_SMS_HOOK_SECRET` in Auth and Edge Function secrets.

OTP codes and provider credentials are never handled by the React client.

## Production build and deployment

Create an optimized frontend build:

```bash
npm run build
```

The generated files are written to `dist`. Route-level lazy loading and manual vendor chunks are used to keep the initial application bundle smaller. Hashed assets are intended to be cached for one year, while `index.html` must be revalidated after deployment.

On Windows, the npm deployment command runs the PowerShell script:

```bash
npm run deploy:web
```

On Linux or macOS, run the Bash version directly:

```bash
bash scripts/deploy-web.sh
```

The deployment environment must provide:

```env
ARVAN_ACCESS_KEY=
ARVAN_SECRET_KEY=
ARVAN_ENDPOINT=
ARVAN_PUBLIC_BUCKET=
```

After deployment, cache headers can be checked with `npm run verify:cache` on Windows or `bash scripts/verify-cache-headers.sh` on Linux and macOS.

The committed CORS and bucket-policy JSON files document the required ArvanCloud configuration for public and private storage. Review their allowed origins before using them in another environment.

## Security notes

- Do not commit `.env`, `.env.test`, storage credentials, service-role keys, or test authentication state.
- Treat the Supabase anon key as a public client identifier and enforce access through RLS.
- Keep private buckets inaccessible to anonymous object reads.
- Deploy privileged storage and account operations only as Edge Functions.
- Apply database changes through new migrations instead of editing migrations that have already been deployed.
- Use separate test accounts and storage buckets when running destructive end-to-end tests.
